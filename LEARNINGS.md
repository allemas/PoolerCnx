# Overview

A toy connection pool I built as a learning exercise.
The implementation is currently single-threaded; concurrency comes next.

For design decisions and trade-offs, see [`DESIGN.md`](./DESIGN.md).
For development workflow, see [`WORKING.md`](./WORKING.md).

## What was built

**`PoolEntity<T>`** wraps a raw connection together with the metadata
the pool needs to manage it: a lifecycle state, a pool-local
identifier, and a recycling callback. It implements `AutoCloseable`,
so users release entries via try-with-resources. `close()` returns
the entry to the pool; `destroy()` is the only path that actually
tears down the underlying connection.
([ADR-001](./DESIGN.md#adr-001), [ADR-002](./DESIGN.md#adr-002))

**The lifecycle is a small state machine** with three states:
`IDLE`, `IN_USE`, and `CLOSED`. Transitions are explicit and
guarded — `markUsed()` requires `IDLE`, `close()` requires `IN_USE`,
`destroy()` is reachable from any non-closed state. An earlier draft
included an `UNKNOWN` state that I removed: it represented "I haven't
thought through this case", which is a modeling smell rather than a
real state. Each invalid transition throws explicitly, which has
already caught several bugs during development.
([ADR-003](./DESIGN.md#adr-003))

**`DefaultPool<T>`** holds a single list of `PoolEntity<T>`,
eagerly creates `minIdle` entries on construction, and grows up
to `maxSize` on demand. `acquire()` scans for an idle entry,
creates a new one if room allows, or throws when saturated. Each
entry receives a `Consumer<PoolEntity<T>>` callback at construction,
invoked on close to notify the pool of the release.
([ADR-005](./DESIGN.md#adr-005), [ADR-006](./DESIGN.md#adr-006),
[ADR-007](./DESIGN.md#adr-007))

**Identifier strategy** — entity IDs are generated by an
`AtomicInteger` owned by the pool instance, not by a static field.
Each pool has its own sequence starting at zero, which keeps logs
readable and tests deterministic.
([ADR-004](./DESIGN.md#adr-004))

**Tests** — unit tests use a `StubCnx` test double to exercise the
lifecycle without JDBC overhead. JDBC integration tests run against
an in-memory H2 database and verify that the design doesn't break
the contract of the wrapped resource.

## Learnings

- **Model state transitions, not forbidden states.** My first version
  of `close()` threw when state was `IN_USE`, the only state where it
  should have succeeded. Reasoning in terms of "from X, only transition
  to Y is allowed" is clearer than "if state is X, refuse". State
  machine guards should express the valid path, not the forbidden one.

- **try-with-resources is for resources you consume, not produce.**
  A factory method I wrote initially wrapped its newly-created entity
  in a try-with-resources block before returning it. The block
  auto-closed the entity on return, putting it in `IDLE` before the
  caller could use it. Constructing-to-return and using-locally are
  opposite lifecycles — the same syntactic pattern fits one and breaks
  the other.

- **The wrapper and the wrapped have separate lifecycles.** Calling
  the underlying `Connection.close()` (via `try (Connection c = pool.acquire().getConnexion())`)
  destroys the JDBC resource while leaving the `PoolEntity` referencing
  a dead connection. The pool then hands out the corpse on the next
  acquire. Users must `try` on the wrapper, not on the wrapped.

- **`Consumer<T>` and `Function<T, R>` are not interchangeable.** The
  recycling callback is a side effect with no useful return value, so
  I typed it as `Consumer<PoolEntity<T>>`. Typing it as
  `Function<X, Void>` would have forced a parasitic `null` return
  everywhere and obscured the intent. The chosen type is documentation:
  it says "side effect, no result", mirroring `IO[Unit]` in Scala.

- **Decoupling via callback enables isolated testing.** Passing the
  recycling effect as a `Consumer` rather than the `Pool` instance
  means `PoolEntity` can be tested without any pool at all — pass any
  `Consumer` that records what it receives, and the entity's lifecycle
  is fully observable in isolation.
